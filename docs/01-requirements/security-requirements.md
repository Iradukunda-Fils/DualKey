# Security Requirements Specification

**Document ID:** `DOC-01-SEC`  
**Status:** Implementation Baseline  
**Version:** 1.0.0  
**Date:** September 29, 2026  

---

## 1. Security Context & Threat Baseline

DualKey protects a physical boundary by enforcing strict identity binding between physical possession and biometric characteristics. As an educational and systems engineering prototype, the security architecture balances rigorous software boundary isolation with candid disclosures regarding hardware and biometric limitations.

---

## 2. Requirement Specifications

### SEC-001: Two-Factor Correlation
* **Statement:** An access grant shall require both valid RFID possession and matching biometric facial identity for the exact same registered identity within the active session window.
* **Specification:**
  ```text
  ACCESS_GRANTED =
      valid_rfid
      AND verification_window_active
      AND exactly_one_usable_face
      AND lbph_distance <= configured_threshold
      AND recognized_person == card_owner
      AND stable_match_count >= required_consistent_matches
  ```
  Possession of a card without a matching face, or presence of an authorized face without the corresponding card, must never grant access.

### SEC-002: Closed Default (Fail-Closed Posture)
* **Statement:** The system shall default to the locked state across all phases of the system lifecycle, including boot, idle, error, network/serial severance, and power interruption.
* **Specification:** In the absence of an explicit, valid, unexpired `ACCESS_GRANTED` command, the servo must remain firmly at $0^\circ$ (locked). Any anomaly, unexpected token, sensor failure, or unhandled exception must immediately resolve to access denial.

### SEC-003: Command Safety & In-Process Authority
* **Statement:** Actuator commands to unlock physical hardware shall be accepted by the device adapter only if generated by the authorized in-process `AccessController`.
* **Specification:** The device driver (`Esp32SerialAdapter`) shall verify that incoming grant requests originate from an active `AccessSession` managed by the authoritative domain controller. Peripheral adapters or external interfaces shall not expose independent methods to drive the servo open.

### SEC-004: Replay and Stale Command Protection
* **Statement:** The system shall detect and reject replayed, delayed, or stale commands.
* **Specification:** Every `access_command` transmitted from the host shall incorporate a unique UUIDv4 `command_id` and the associated `session_id`. The ESP32 shall maintain a cache of the most recently processed command ID. If a duplicate command ID arrives, or if a command references an expired session, the ESP32 shall reject execution without actuating the servo.

### SEC-005: Single Decision Point
* **Statement:** Exactly one software component shall possess authority to issue access determinations.
* **Specification:** All authorization evaluations are strictly centralized within the host's `AuthorizationPolicy`. The ESP32 firmware, camera driver, RFID listener, and database repositories are strictly prohibited from evaluating access rules or executing unilateral unlocks.

### SEC-006: RFID Security Limitation Disclosure
* **Statement:** System documentation and security architecture shall explicitly document that standard 13.56 MHz MFRC522 card UIDs are vulnerable to RF sniffing and cloning.
* **Specification:** The system treats the RFID UID strictly as an unauthenticated identity identifier, analogous to a username, rather than a cryptographic proof of identity. The primary defense against cloned cards is the mandatory second biometric factor.

### SEC-007: Biometric Security Limitation Disclosure
* **Statement:** System documentation and security analysis shall explicitly state that OpenCV's LBPH face recognizer does not incorporate presentation-attack detection (liveness detection).
* **Specification:** The prototype is vulnerable to 2D presentation attacks, such as holding a high-resolution printed photograph or smartphone screen in front of the camera. The system must never be represented or marketed as possessing anti-spoofing capabilities.
